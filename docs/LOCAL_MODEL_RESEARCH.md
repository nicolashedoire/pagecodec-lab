# Local decision models in the proposed OS

Status: **research and integration plan**, 2026-10-30. No decision model currently runs in the project's experimental bare-metal QEMU guest. In particular, no local Jev weights or local Jev inference have been verified. The existing Laya demonstration ran separately on the macOS host and did not control the system.

## Jev and the independent Laya experiment

[TypeSafe's Jev documentation](https://docs.typesafe.ai/introduction) describes a hosted decision model taking a state and typed questions and returning structured outputs such as choices, scores and probabilities. The [quick start](https://docs.typesafe.ai/introduction/quickstart) documents its API. This project takes Jev as the owner's design reference, but has not located or verified a downloadable official Jev checkpoint. A different decision model or a similarly shaped response is not Jev or proof of equivalent behavior.

The separate [`local_decision`](../experiments/local_decision/) experiment used [Laya-MLX](https://github.com/mizorewww/laya-mlx), a different open model/runtime, with the [Laya multilingual MLX checkpoint](https://huggingface.co/aac6fef/laya-multilingual-mlx). Its pinned weights occupy 643,835,426 bytes (about 614 MiB). The model card describes an mmBERT-based encoder, tokenization, a decision transformer and scoring/action heads. The independently published [original Laya multilingual model card](https://huggingface.co/convaiinnovations/laya-multilingual) lists its architecture and known calibration and task limitations. A format parser alone does not reproduce those components or their behavior.

The repository records two executions of one synthetic scenario on the research Mac. In both, Laya suggested more compression despite the scenario specifying sufficient memory and a busy CPU. The two observations had approximately 803 and 920 MiB peak process RSS; load times and inference times differed considerably. See the [experiment report and recorded outputs](../experiments/local_decision/README.md) for versions and exact measurements. This one scenario is neither a general quality benchmark nor a measurement of the future VM. It also does not change the owner's Jev assumption; it shows only that this independent Laya checkpoint must not be assumed equivalent to Jev or used as a verified system policy.

## Current VM resources and interfaces

The [graphical guest](../experiments/dual_pointer_display/) runs with 128 MiB of virtual RAM, a fixed 8 MiB non-reclaiming heap, one CPU and no model loader, inference engine, general filesystem or persistent model storage. Its MCP subset exposes synthetic pointer and document tools over serial; it does not run model inference and its actor labels are not authenticated. The 614 MiB Laya-MLX weight file alone is larger than the entire configured guest RAM. Activations, tokenizer data, runtime state, queues and the rest of the OS would require additional space. Increasing the VM's RAM would be necessary for a full resident copy but would not itself provide allocation, loading, execution, isolation or sufficient inference speed; streaming or quantization would require their own validated designs.

The [MMU guest](../experiments/virtual_memory/) demonstrates a narrow identity mapping and selected permission checks in a separate VM. It is not integrated with the graphical guest and does not supply general-purpose address spaces. Other experiments demonstrate synthetic VirtIO storage and controlled scheduling, but not a filesystem, an isolated model process, authenticated IPC or the complete OS runtime required by an inference engine. The timer-driven [integer-only switching experiment](../experiments/preemptive_demo/) does not preserve FP/SIMD or other extension state.

The existing Laya-MLX route depends on the MLX/macOS/Apple Silicon environment described by its maintainers; the guest currently provides neither macOS, its Metal stack, nor a compatible MLX runtime. A local host execution must not be reported as guest execution. Exposing a model by proxy from the host might be a useful integration experiment, but it would be a host service, not inference implemented inside the guest OS. No such bridge is claimed here.

## Reusable candidates, not guest-ready guarantees

- [Candle](https://github.com/huggingface/candle) is a Rust machine-learning framework with CPU and other backends. Whether it supports the exact Laya model architecture, tensor layout, tokenizer and decision heads requires a version-specific audit and numerical comparison. A Rust implementation does not imply `no_std` support or availability in our guest.
- [tract](https://github.com/sonos/tract) provides inference for TensorFlow and ONNX models. A valid conversion/export of the exact Laya graph, coverage of its operators and agreement with the reference would all have to be demonstrated; ONNX is not automatically interchangeable with a Safetensors checkpoint.
- [Safetensors](https://github.com/safetensors/safetensors) is a tensor storage format with Rust implementation; [Hugging Face Tokenizers](https://github.com/huggingface/tokenizers) provides tokenizer implementations. Model configuration, tokenizer and scoring semantics remain necessary alongside tensor bytes. Loading a format is not running the model.
- The [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25) defines a protocol for connecting applications and tools. MCP is not an inference runtime or authentication by itself; an integrated service would need a real identity, authorization and resource-management design in addition to protocol conformance.

These candidates target environments with capabilities such as a Rust standard library, allocator, files, threads, memory mapping, floating point and/or platform backends. Their exact requirements depend on version and chosen features; audit them rather than assuming that they compile for `aarch64-unknown-none-softfloat` or the current `no_std` guest. Native GPU acceleration would additionally require a supported GPU stack; QEMU's current virtual display is not a Metal or Apple Neural Engine interface. Check each code, model and conversion license before redistribution.

## Proposed VM-first route

1. Define a versioned, size-bounded model artifact and loader contract: exact file format, tensor names, dimensions and numeric types, tokenizer/configuration, revision, trusted hash or signature, maximum sizes and deterministic failure behavior. Exercise malformed lengths, offsets, missing tensors and mismatched hashes on synthetic data. Host-downloaded manifests and hashes establish consistency only to the trust placed in their source.
2. Provide a guest storage path for test artifacts and a reclaiming allocator with explicit memory budgets. Connect actual guest storage and memory services rather than assuming the separate synthetic persistence experiment is already a model filesystem. Isolate parsing and inference in a constrained service once real process/address-space isolation exists; until then use fictional artifacts only and make the limitation explicit.
3. Implement or port a minimal CPU inference path. Verify tokenization, each tensor operation and final typed outputs against a pinned reference with exact test vectors and tolerances. If floating point, SIMD or threads are used, first supply and test the corresponding context switching, ownership and synchronization. Quantized or streamed alternatives need their own error, correctness and performance tests; smaller files do not automatically preserve decision quality.
4. Run a genuinely trained, appropriately licensed small model in the VM only after the required operations are implemented; a tiny hand-authored linear scorer can exercise data plumbing beforehand but must be labeled a synthetic fixture, not Jev, Laya or a trained model. Measure model storage, peak resident memory, latency and CPU cost on representative workloads, separating load time and cold/warm conditions.
5. Evaluate Laya's specific graph and tokenizer and compare with a reference before considering its outputs interchangeable across runtimes. Evaluate decision quality, calibration, failure modes and the cost of predictions for the intended system decisions. Use typed, bounded requests and results through an authenticated control service, with a deterministic fallback and an action-validation layer. Do not place model inference in an interrupt handler or assume a probability is a guarantee.

All project execution tests are to run in VMs. A pass in QEMU would establish only the tested VM environment; it would not prove native M4 Pro drivers, GPU acceleration or readiness to install the system on a Mac.
