# Two pointers in an AArch64 QEMU guest

This is a small experimental bare-metal Rust guest, not a general-purpose OS or a macOS replacement. It draws two panels with the QEMU virtio GPU 2D device. A QEMU virtio tablet controls the human pointer; an experimental MCP server in the guest can move the AI pointer. The panels are graphical mockups: they are not isolated processes, real workspaces, windows, or applications.

The server supports a small subset of MCP 2025-11-25 over newline-delimited JSON-RPC on the guest PL011 serial port: `initialize`, `notifications/initialized`, `ping`, `tools/list`, and `tools/call`. Pointer tools are `pointer_state` and `move_ai`; `move_remote` and `remote_state` control and inspect a third, synthetic logical actor that has no visible cursor or window. `document_edit`, `document_view` and `document_merge` operate on a single synthetic in-memory document through `workspace_bridge`. A successful `move_ai` response is sent only after the frame has been redrawn and flushed. The non-rendered remote actor has no framebuffer update. `move_ai` accepts integer `x` in 400–773 and `y` in 0–573. It does not implement clicks. The guest is intended only for an isolated demonstration: its serial endpoint has no authentication, and it implements neither access control nor security isolation.

The demo boots on QEMU's `virt` machine with a single AArch64 CPU and 128 MiB RAM, uses a fixed framebuffer, 512-byte message line and a simple non-reclaiming bump allocator. It accepts 64 requests or notifications per boot, including invalid or oversized lines, and then stops; restart the VM for a new session. This bound reduces memory exhaustion but does not make the guest robust against adversarial clients. It has no persistent storage, networking, host file sharing, keyboard, scheduler, model inference or access to actual documents through its MCP tools. Human tablet movements and MCP assistant movements are routed through the [`dynamic_input` prototype](../dynamic_input/); its per-actor states drive the display and `pointer_state`. The guest pre-registers exactly three actors; it does not expose actor creation or a real remote connection. The document bridge binds caller-provided human and assistant labels to their respective synthetic copies; its actor registry and the pointer router’s workspace state are separate and are not synchronized with one another; these labels are forgeable and are not authentication. The MCP edit and view tools accept actor, space and a key of up to 32 bytes; edit also accepts a value of up to 64 bytes or null for deletion. Merge reports field values, net-change origins and conflicts, and refuses to materialize a complete conflicting document. There is no AI conflict resolution, persistent storage or document revision check. The human click indication is only a visual effect and is not routed as a click or focus event. Actor labels and assignments are constructed inside the guest and do not authenticate actors or enforce an operating-system security boundary. The guest routes moves through a preallocated 64-entry circular journal: it records actor and workspace slots, position and outcome without allocating per movement. Once full, it overwrites the oldest record and counts losses. The registry’s unbounded movement log is bypassed on this path, so the ring is not a complete audit history. It relies on `virtio-drivers` 0.13.0, which does not verify a device's `FEATURES_OK` acceptance after negotiation; this experiment only demonstrates QEMU accepting its devices.

Text is rendered using antialiased glyphs generated from **Inter**, designed by Rasmus Andersson and distributed under the [SIL Open Font License 1.1](assets/OFL.txt). The unmodified variable font is included at `assets/Inter-variable.ttf` (SHA-256 `29160a80ff49ddcab2c97711247e08b1fab27a484a329ce8b813d820dc559031`); source: [Google Fonts, Inter](https://github.com/google/fonts/tree/main/ofl/inter). `assets/generate_font.py` generates the glyph cells with Pillow; the running guest has no Python dependency.

Compile the guest for `aarch64-unknown-none-softfloat` with `cargo build --release --locked`, then launch the resulting ELF, using QEMU's native Cocoa backend on macOS or another available backend:

```sh
DEMO_DIR=$(mktemp -d)
chmod 700 "$DEMO_DIR"
qemu-system-aarch64 -M virt,virtualization=off -accel tcg -cpu cortex-a57 \
  -smp 1 -m 128M -nodefaults -device virtio-gpu-device -device virtio-tablet-device \
  -display cocoa -nic none -monitor none -no-reboot \
  -chardev "socket,id=mcp,path=$DEMO_DIR/mcp.sock,server=on,wait=off" \
  -serial chardev:mcp -kernel target/aarch64-unknown-none-softfloat/release/dual-pointer-display
```

Use a private socket path and connect one MCP client at a time; filesystem permissions are not authentication. Only expose this unauthenticated socket locally for the duration of an isolated test. The client must initialize the MCP session, send `notifications/initialized`, then use the listed tools. A serial socket disconnect does not reset guest state. A restarted VM resets all state. Remove the empty temporary directory after QEMU exits.

## Repeat the end-to-end demonstration

Compile this guest and the separate [`vm_mcp_client`](../vm_mcp_client/) first. All document edits in the demonstration are synthetic MCP requests, not changes to host files. The Python standard-library harness runs QEMU, injects **synthetic** tablet events using QMP, runs 1,101 synthetic human movements, verifies the final position, bounded journal and zero guest heap allocation during those moves, then checks a further QMP tablet event reaches x=390 and restores the standard scenario, runs the compiled Rust client against the guest MCP server, verifies both pointer positions and exercises a third logical actor without changing either displayed pointer, then sends MCP document edits, reads, a rejected cross-space edit and merge requests to check copy separation, provenance and retained conflict values. It saves a genuine QMP framebuffer dump and a JSON trace. It uses a temporary private socket directory, no network, disks or shared host directories. A host-side client and harness only transport commands; the guest code executes inside the VM.

```sh
python3 run_demo.py --qemu /path/to/qemu-system-aarch64 \
  --guest /path/to/dual-pointer-display --client /path/to/vm-mcp-client \
  --output-dir /path/to/output
```

The default is headless; add `--cocoa --hold 30` on macOS to show the window for 30 seconds after the capture. `framebuffer-before.ppm` and `framebuffer.ppm` are before/after framebuffers exported by QEMU. The harness checks that their hashes differ; `evidence.json` records both hashes, QEMU version, binary hashes and the protocol exchange. This is neither a benchmark nor evidence of human physical input. The script waits for the guest framebuffer to become ready, with a bounded timeout; `--startup-wait` optionally adds a minimum wait before that check. It terminates its QEMU instance after the demo. Do not rebuild the supplied binaries while the demo runs.

The runner bounds each tablet-event poll to 12 requests and makes at most 55 guest messages in its successful worst-case path, below the 64-message guest limit. This leaves limited room for slower execution: if an event has not arrived after the bounded poll, the run fails rather than asserting success.
