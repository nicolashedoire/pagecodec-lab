# VirtIO feature acceptance experiment

This is a freestanding AArch64 Rust guest running under QEMU. It investigates a specific gap in the `virtio-drivers` 0.13.0 initialization sequence; it is not a complete driver or a patch to that dependency. The exact dependency versions are pinned in `Cargo.lock`.

For a **modern** device, [VirtIO 1.2 section 3.1.1](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html) requires the driver to re-read device status after setting `FEATURES_OK` and stop initialization if the bit did not remain set. The legacy interface omits this acceptance step. In the published [`virtio-drivers` 0.13.0 transport](https://docs.rs/virtio-drivers/0.13.0/virtio_drivers/transport/trait.Transport.html), `begin_init` sets `FEATURES_OK`, calls `set_guest_page_size` and returns negotiated flags without reading back that status. This is a code-level observation, not a claim that QEMU normally rejects its supported features.

## What the guest demonstrates

1. An **in-guest simulated transport** offers `VERSION_1` but removes `FEATURES_OK` when the driver sets it. The actual upstream `Transport::begin_init` returns flags and calls `set_guest_page_size` despite the simulated refusal. The counter observes a method call, not necessarily a hardware write: the upstream method is a no-op for modern VirtIO-MMIO.
2. A separate, experimental `checked_begin` implementation re-reads status immediately. For that same simulated refusal it sets `FAILED` and returns an error without setting up a queue or setting `DRIVER_OK`. These latter counters are narrow observations: `checked_begin` never performs those later initialization steps even on acceptance, so this does not test a complete driver's fail-closed behavior.
3. A **real QEMU modern VirtIO-MMIO RNG** is then negotiated up to, but not including, queue setup. The guest reads back `FEATURES_OK` set on that device. No random data or real user data is requested.
4. Two separate VM runs also verify that an absent RNG and a legacy VirtIO-MMIO RNG are rejected by the modern-only experiment. Their serial `FAIL` markers are expected negative outcomes; the harness checks them.

The refusal is modeled in Rust inside the VM, not generated by a real rejecting QEMU or physical device. The actual QEMU run establishes only the accepted path up to `FEATURES_OK`; it does not exercise queue operations, interrupts, I/O, device recovery or a physical Apple device. The mock implements only the trait methods needed for this scenario. The guest does not modify the existing dependency, and the prototype does not replace the drivers elsewhere in the repository. The experimental routine supports only a modern common-feature subset and must not be treated as a production or fully compliant VirtIO implementation; it does not handle legacy initialization, asynchronous reset completion, all transport semantics, ordering, timeouts or all required feature dependencies. Reset-incomplete, missing-version and `DEVICE_NEEDS_RESET` branches are not exercised here.

A possible upstream integration would change the initialization API to return an error on a refused modern negotiation, perform the status read before device-specific setup and update every device constructor to propagate that error. Legacy handling and asynchronous reset semantics need their own design and tests. This repository does not implement that upstream change.

## Reproduce

Install Rust with target `aarch64-unknown-none-softfloat`, QEMU AArch64 and Python 3. From this directory:

```sh
cargo fetch --locked
cargo build --release --locked --offline
python3 run_demo.py --qemu /path/to/qemu-system-aarch64 \
  --guest target/aarch64-unknown-none-softfloat/release/virtio-negotiation-lab \
  --output-dir /path/to/output
```

The harness launches three QEMU TCG VMs with no disks, network or host directory sharing. QEMU is configured with `/dev/zero` as a non-sensitive RNG backing source; the guest never asks for RNG bytes. It records a hash of the image before and after the trials, the QEMU version, and serial output. Do not rebuild the image while the test runs. See the [recorded synthetic output](evidence/virtio-negotiation-evidence.json).

The source package and QEMU are not vendored here.
